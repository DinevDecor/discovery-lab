# Deliverable 7 — Consequences of REJECT

"Reject" here means: none of the three variants is accepted as
`discovery-lab`'s mandate, and `PROP-0001` in its current form is
declined.

## Immediate, mechanical consequences

- `discovery-lab` continues to operate — as it has throughout this
  session — without a ratified mandate. `ARCH-001`'s `R1` (the
  ecosystem's own top-ranked architectural risk) remains live and
  unresolved rather than closed.
- Per `PROP-0001`'s own precedent rule (the "Dinev Decor Systems" row
  discussion cited in Deliverable 5), `discovery-lab` would remain
  ineligible for a `project-memory/PROJECT_REGISTRY.md` row —
  unchanged from the current state, not a new restriction.
- `Ecosystem Health Review v0.1` does not run under this mandate's
  authorization; it would need either a revised proposal or a different
  authorizing decision.

## Consequences for existing work — what does and does not become invalid

- **Does not become invalid**: the factual content of `AG-002`'s 7 real
  runs, `AG-003`'s 3 real curation passes, the Reality Stress Test's
  4/4 `PASS` verdicts, `EXEC-001`'s real filed Knowledge Object, and
  every architectural finding in `ARCH-001`/`ARCH-002`/`G2`. These are
  observations and executed work, not claims of organizational
  authority — rejecting a mandate does not retroactively make a
  citation false or a file not exist.
- **Does become explicitly unauthorized, retroactively**: the
  organizational standing under which that work was performed.
  `AG-002` and `AG-003`'s `FROZEN v1.0` status would need an explicit
  decision on its own continued meaning — `GOVERNANCE.md` itself
  defines `FROZEN` as an architecture-stability claim independent of
  adoption, but the repository's basic authorization to exist and
  operate at all (Principle 0's own frame: "Discovery Lab never creates
  truth... proposes next steps... for the owning repository to accept
  or reject") is exactly what `PROP-0001` was written to establish. A
  `REJECT` verdict does not automatically un-freeze `AG-002`/`AG-003`,
  but it leaves their operating authority resting on nothing, which is
  a more exposed version of the current `DRAFT`-mandate state, not a
  new problem — `ARCH-001`'s `R1` risk materializes rather than
  resolves.

## What REJECT does not by itself provide

`PROP-0001`'s own text offers no fallback mandate — rejecting the
current proposal does not produce a replacement one. A `REJECT`
decision would leave `discovery-lab` needing either a revised `PROP-000x`
proposal or an explicit decision to continue operating without a
ratified mandate (a decision distinct from, and not automatically
implied by, rejecting this specific document). This package does not
draft that fallback — doing so would be creating a new proposal, which
this task's own rules forbid.

## Symmetry with ACCEPT

Both ACCEPT and REJECT close `ARCH-001`'s `R1` in the sense that both
are *decisions* rather than continued deferral — `R1`'s actual harm, per
`ARCH-001`'s own framing, is the *unresolved sequencing* (Roles frozen
ahead of mandate ratification), not a bias toward either outcome. Only
continuing to defer the decision leaves `R1` exactly as open as it has
been since `ARCH-001` first named it.
